## 1. Where Kalshi actually is

### What we know for certain (MEASURED from the laptop, 2026-09-24 ~03:30 ET)

Kalshi publishes two ways in: the normal web API (`api.elections.kalshi.com`, which
the bot and the recorder use) and a professional "FIX" line
(`mm.fix.elections.kalshi.com`, `marketdata.fix.elections.kalshi.com`,
SOURCE: https://docs.kalshi.com/fix/connectivity). The web API sits behind
Amazon CloudFront, a worldwide relay layer, so its address tells you nothing
about where the exchange is. The FIX hosts are NOT behind the relay, so their
addresses do.

I resolved every host and looked each address up in Amazon's own published
address list (`https://ip-ranges.amazonaws.com/ip-ranges.json`, file dated
2026-09-24-03-27-06):

| host | address | Amazon says |
|---|---|---|
| `mm.fix.elections.kalshi.com` (order entry) | 18.119.210.162, 18.223.244.34 | **us-east-2 (Ohio), EC2** |
| `marketdata.fix.elections.kalshi.com` | 18.220.63.230 | **us-east-2 (Ohio), EC2** |
| `trading-api.kalshi.com` | 77.112.123.133, 18.227.137.121 | **us-east-2 (Ohio), EC2** |
| `api.elections.kalshi.com` (what the bot uses) | 108.138.64.71/.97/.103/.104, 3.167.37.x | CloudFront, GLOBAL (a relay, not a location) |
| `fix.demo.kalshi.co` (the demo exchange) | 44.228.105.65, 44.237.38.67 | us-west-2 (Oregon) -- the demo is on the other coast |

Two more facts from the same probe: the relay node the laptop is sent to is
`IAD61` -- that is **Ashburn, Virginia**, not New York (response header

So today's path for every price update and every order is roughly:
laptop -> Wi-Fi -> Verizon -> Ashburn relay (20 ms) -> Ohio (14 ms) -> back.

- TradoxVPS (a VPS seller): "Kalshi's order-matching engine runs in AWS

- QuantVPS (another VPS seller) claims Kalshi is "in the Chicago metro" on the

  ping hits a CloudFront relay in Chicago, not the exchange. Their own page
  admits "Kalshi does not publicly share the precise locations of its
  servers". Treat as wrong. SOURCE: https://www.quantvps.com/blog/kalshi-servers-location
- Kalshi itself: "cloud-native architecture on Amazon Web Services" (SOURCE:
  https://kalshi.com/security) and offers AWS PrivateLink to big customers

  anywhere public; its engineering job ads mention AWS, EC2, Kubernetes,

**Verdict: Ohio (`us-east-2`) is confirmed by the address lookup. Nothing
public contradicts it.** One caveat, honestly stated: the address lookup shows
where Kalshi's order-entry front door is. The matching engine could in theory
be elsewhere behind it, but nobody puts a FIX gateway in a different region
from the engine it feeds -- that would add the very delay the gateway exists
to remove. I rate that residual doubt at "not worth a dollar".

### What the CloudFront relay means for choosing where to rent

The bot's WebSocket (`wss://api.elections.kalshi.com/trade-api/ws/v2`) and its
REST orders both go through CloudFront. CloudFront always sends you to the
relay node nearest YOU, then carries the traffic to the fixed origin in Ohio.
So:

- Renting in **Ohio** puts both legs inside one region: expect **about 1-3 ms**
  total instead of today's ~29 ms. (Inferred, not yet measured -- the first
  thing to run on the new machine is the same 5-handshake probe above.)
- Renting in **Virginia or Chicago** gets the relay leg to ~1 ms but keeps the
  ~14 ms relay-to-Ohio leg.
- Renting in **New Jersey or New York** is roughly the laptop without the
  Wi-Fi: ~20 ms.

Is 28 ms worth chasing? In plain terms: the bot buys in the last seconds
before a close, on the strength of index prints that arrive once a second. A
28 ms head start is 3% of one print interval -- not a strategy change, but it
is the difference on the fills where someone else is racing us for the same
offer, and CURRENT_STATE says offers at our confidence "fell 54%" since we
started arriving late. The bigger wins from the move are not latency at all:
no more Wi-Fi drops (the 4 h 47 min outage of 09-22), no Windows-Update
reboots (7.57 h lost on 09-15), a disk that is not 98% full, and a clock that
is set properly (see 5.4).

### Path A -- Windows Server on the cloud computer (recommended)

- **Porting: about a day.** Install Python 3.14 + the three packages, clone
  the repo to `C:\kals-repo`, copy `C:\kals` (scripts, keys, `telegram.json`,
  NOT the tape), register `KalsBoot` with `boot_all.ps1 -Install`, and set it
  to "run whether user is logged on or not" (an open item from
  CURRENT_STATE even on the laptop). Every script runs unchanged. The
  desktop app runs inside a Remote Desktop session; you open Remote Desktop
  from the laptop (or the phone app) and see the same window you see today.
- **Cost:** Lightsail Windows 16 GB **$124/mo**; roughly **$40/mo more than
  Linux** on Lightsail, $50-60/mo more on EC2.
- **Two things to set on day one**, because they are the failures that hit
  the laptop: (1) Windows Update -> "notify, never auto-install" (Group
  Policy: Configure Automatic Updates = 2), so the server never reboots
  itself; (2) the `KalsBoot` task -> run at startup without a login.
- **Risk:** low. It is the same programs on the same operating system. What
  changes is the network path and the clock, both for the better.

### Path B -- Linux

- **Porting: 7-10 working days, call it 1-2 weeks**, plus 2-3 calendar days
  of paper-parallel running before cutover. Breakdown:
  - paths -> environment variables (`KALS_ROOT`, `KALS_RESULTS`,
    `KALSHI_KEY_FILE`, `TELEGRAM_CONFIG`), with self-tests: 1 day
  - one shared "list python processes / is pid alive" helper from `/proc`,
    replacing the PowerShell calls in `pinphone`, `pindesk`, `pintool`,
    `pinmobile`, `pinflat`: 1 day
  - `restart_bot.ps1` -> a Python launcher with the SAME rails (pinflat
    check, prove the old pid is gone, never two live bots, write the
    VERSIONS entry) and a self-test that proves it refuses when it should:
    2-3 days. **This is the risky part; it touches the money rails.**
  - `run_all` / `watch_bot` / `boot_all` -> systemd units (`Restart=always`,
    start on boot, a 5-minute timer for the deaf-recorder and disk checks,
    the STOP-flag and drawdown-hold logic as a small Python pre-start
    check): 2 days
  - `sync_arms.ps1` -> Python reading the live bot's command line from
    `/proc`: 1 day
  - control surface: Telegram already works; the status page is
    `pinmobile.py` regenerated every minute and served on a private
    address (Tailscale or an SSH tunnel -- never an open port): 0.5-1 day
- **Cost:** Lightsail Linux 16 GB **$84/mo**, or EC2 `m7i.xlarge` ~$91/mo on
  a 1-year commitment.
- **What you gain besides money:** no forced reboots ever; `systemd` replaces
  ~2,900 lines of watchdog PowerShell that has itself caused incidents
  (double-bot 09-14, silent deaths 09-15, the stray-comma abort); a clock
  that is checked continuously.
- **What you lose:** the desktop window. You would run the bot from Telegram
  and read the numbers on a web page.

### Recommendation

**Path A now.** The standing priority is "lose less" and the laptop's real
risks -- a 98%-full disk, Wi-Fi, forced reboots, a clock checked every 9
hours -- are removed within days by A at near-zero code risk. B saves about
$40-60 a month and is a better long-term home, but it means 1-2 weeks of
rewriting the scripts that guard real money while the strategy is still
changing daily, and the operator loses the app he actually uses. Do B later,
if at all, as a planned second step on the same Amazon account once the Ohio
machine has run quietly for a month.

## 5. The move, step by step

Rule that governs every step: **at no moment are there two live bots, and at
no moment is nothing recording.** Recorder first, bot last, laptop kept as a
stopped standby.

### 5.0 Before touching the cloud
1. Upload the existing 98 GB tape off the laptop (section 4). ~3 hours.
2. Ask Kalshi support, in writing, whether trading from a rented server in
   Ohio is fine with them, and keep the answer. It is normal (their docs
   offer AWS PrivateLink to big customers), but the account is in the
   operator's name and the rules are theirs.
3. Get the Amazon account set up by the operator himself, with two-factor on
   the root login, a spending alarm at $200/month, and a separate limited
   user for the session to work with. The operator holds the root password.

### 5.1 Rent and harden (day 1, ~2 hours)
1. Lightsail, region **Ohio (us-east-2)**, Windows Server 2022, 16 GB plan.
   Snapshot it once bare so a clean machine can be re-made in minutes.
2. Firewall (Lightsail "Networking" tab): inbound **only** Remote Desktop
   (3389) and only from the operator's home address, or -- better -- install
   Tailscale on the server and the laptop and open nothing at all to the
   internet. Nothing else inbound. The Telegram bot needs no inbound port
   (it polls out). Outbound: leave open (Kalshi, Telegram, exchanges, NTP).
3. Windows Update -> notify only, never auto-install, never auto-reboot.
4. Clock: point Windows time at Amazon's in-region time source
   `169.254.169.123` (Amazon Time Sync; falls back to `time.aws.com`) with a
   short poll interval. Verify with `w32tm /query /status`: the reported
   error bound should be thousandths of a second. **On the laptop today
   (MEASURED): synced to `time.windows.com`, checked every 32,768 s (9.1
   hours), last check 9/23 8:12 PM, error bound reported as 3.96 s.** The
   bot decides in the last 30 s before a close from a wall clock; a clock
   that can be a second out is a real, unmeasured risk that this move
   removes. Also add a startup check to `pinrun` later: compare local time
   to the exchange's `Date` header and refuse to trade if they differ by
   more than 0.5 s (a code change; VERSIONS entry).
5. Install Python 3.14, `pip install cryptography websockets==17.0.1
   requests`, `git clone` the repo (branch `claude/file-uploads-70rtjl`) to
   `C:\kals-repo`, create `C:\kals` with `kalshi_data`, `feed_data`, `logs`,
   `fulltape` folders and the scripts from the laptop's `C:\kals`
   (`kalshi_collector.py`, `crypto_feeds.py`, `run_all.ps1`,
   `kalshi_fulltape.py`, `cdc_record.py`).
6. Run every self-test on the new machine: `python research/pinrun.py
   --selftest`, `pintake`, `livebook`, `pinphone`, `pinracearm`,
   `kalshi_collector`, plus `python research/versioncheck.py` and
   `python research/deploycheck.py`. All green or stop here.

### 5.2 Secrets (by hand, never through git or email)
Copy over the Remote Desktop session (or `scp` over Tailscale):
- `C:\kals\kalshi.pem` (the live signing key; the key ID `5163259c-...` is
  already in `run_all.ps1` and is not secret) and `C:\kals\kalshi-demo.pem`
- `C:\kals\telegram.json` (bot token + pairing secret)
- `C:\kals\keyname.txt`
Lock each file to the service account (`icacls ... /inheritance:r /grant:r
<user>:R`). Prove the key works with a read-only balance call from the new
machine before going further. Consider making a NEW Kalshi API key for the
server and revoking the laptop's when the move is done -- then the standby
laptop cannot trade by accident.

### 5.3 Recorder first (days 1-3)
1. Start `run_all.ps1` on the server (both recorders). The laptop's keep
   running -- two read-only subscriptions on one key is already how the bot
   and recorder share the key today.
2. After 24 hours compare, hour by hour, file sizes per channel on both
   machines and run `python research/tapegaps.py` on both. Sizes within a
   few percent and no extra gaps on the server = the server tape is good.
3. Only then stop the laptop's `run_all.ps1` (or keep it as a second copy
   until the disk says otherwise; at 20 GB free it has about 5 days).

### 5.4 Paper bot on the server beside the live bot on the laptop (days 2-5)
1. Run `pinrun.py` on the server WITHOUT `--live`, with exactly the live flag
   list from `restart_bot.ps1` (this is what `sync_arms.ps1` does for every
   arm), for at least 2 days (~200 closes).
2. Compare its decisions to the laptop's live bot close by close (`h2h`, per
   the standing rule "read h2h, not diff"). Expect the server to see each
   index print ~25 ms earlier; a decision that differs at the boundary of a
   second is the latency gain, and each one must be understood, not waved
   through. Anything else that differs is a bug -- stop and find it.
3. Bring the paper fleet up on the server with `sync_arms.ps1` and confirm
   `pinphone` answers `/status` from the server (mute the laptop's phone
   bot first: two Telegram pollers on one token fight over messages).

### 5.5 Cutover (one flat moment, ~10 minutes)
Do it right after a settlement, when `pinflat` says no position is held and
the next close is ~14 minutes away.
1. **Laptop:** create `results\pinrun-live.stop` (the watchdog holds), press
   STOP on the desktop app, then confirm from a terminal that NO
   `pinrun.py --live` process exists:
   `Get-CimInstance Win32_Process -Filter "Name='python.exe'" | Where-Object {$_.CommandLine -like '*pinrun*--live*'}`
   must return nothing. Leave the stop flag in place: `boot_all.ps1` only
   starts the watchdog and the watchdog honours the flag.
2. **Copy the live state files** laptop -> server (they carry the drawdown
   mark, the day-loss cap, the size mirror and the ledger):
   `results\pinrun-hwm.json`, `pinrun-dayloss.json`, `pinrun-live-size.json`,
   `kalshi_ledger.json`, `kalshi_transfers.json`, `lab_control.json`.
   Without `pinrun-hwm.json` the server bot re-bases the 20% drawdown mark;
   without `pinrun-dayloss.json` it forgets today's losses and hands itself a
   fresh $200 (the 09-19 failure, thirteen times over).
3. **Server:** `git pull`, `python research/versioncheck.py`, then
   `powershell -File C:\kals-repo\restart_bot.ps1`, then start
   `watch_bot.ps1` (or just run `boot_all.ps1`). Confirm the `start` record in
   the new `pinrun-live-*.jsonl`, a `watch` record within a minute, and the
   Telegram "started" alert.
4. **Write the VERSIONS.md entry at that moment:** `v-vm-ohio`, UTC time,
   git SHA, "bot now runs on the Ohio server; laptop bot stopped with the
   stop flag", and the revert command (5.7).
5. Watch the first three closes with `/status` and `pinday`. Then measure
   what the move bought: the same 5-handshake probe from section 1, run on
   the server, and the order round-trip fields the bot already logs
   (`t_ms_*` on orders) compared to the last week on the laptop.

### 5.6 Afterwards
- **Laptop = warm standby:** repo kept in sync with `git pull`, keys kept
  (or revoked, per 5.2), stop flag present, desktop app usable for reading.
  Do not let it start a bot: the flag does that, and `KalsBoot` may stay.
- **Monitoring** (the existing alerts move with the code: BLIND, SILENT,
  losses, watchdog heartbeats). Add two external ones, because a dead server
  cannot report itself: (a) Lightsail's own status-check alarm to the
  operator's email/phone; (b) a free dead-man's-switch (healthchecks.io or
  UptimeRobot): `boot_all.ps1` pings it every 10 minutes and the service
  texts if a ping is missed for 20 minutes.
- **Disk alarm** at 40 GB free on the server (the 6 GB rule with real
  headroom), through the same dead-man's service.
- **Snapshots:** one automatic Lightsail snapshot a day (about $0.05/GB-mo of
  changed data; a few dollars a month). It is a rollback for the machine,
  not a backup of the tape -- the tape's backup is the nightly S3 copy.

### 5.7 Rollback (any time, ~2 minutes, only at a flat moment)
1. Server: create `results\pinrun-live.stop`, stop the bot, confirm zero
   `pinrun --live` processes on the server.
2. Copy the six state files in 5.5 step 2 back to the laptop.
3. Laptop: delete `results\pinrun-live.stop`, press START on the desktop
   app. Confirm the `start` record.
4. VERSIONS entry: `v-vm-ohio` reverted, time, reason.
The recorder needs no rollback: leave both running until the situation is
understood; two copies of the tape hurt nothing but disk.
